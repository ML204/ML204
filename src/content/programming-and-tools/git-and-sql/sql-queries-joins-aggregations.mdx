<Section label="What is it?">

**Structured Query Language (SQL)** is the universal domain-specific language used to query, transform, and extract datasets from relational database management systems (RDBMS) and modern cloud data warehouses (PostgreSQL, Snowflake, Google BigQuery, DuckDB, Amazon Redshift).

In machine learning pipelines, raw data rarely starts as a clean Pandas DataFrame or PyTorch tensor. Instead, raw events, user transactions, and sensor logs reside across normalized relational tables. SQL is the primary engine used to:
- Filter and slice millions of records before memory ingestion.
- Join disparate tables (e.g., users, purchases, and browsing sessions).
- Aggregate raw transactional events into tabular training features (e.g., total spend, purchase frequency, rolling averages).

```sql
-- Feature extraction query: Extracting user behavioral features for churn prediction
SELECT 
    user_id,
    COUNT(order_id) AS total_orders,
    AVG(order_amount) AS avg_order_value,
    MAX(order_date) AS last_active_date
FROM orders
WHERE order_date >= CURRENT_DATE - INTERVAL '90 days'
GROUP BY user_id
HAVING COUNT(order_id) >= 2
ORDER BY total_orders DESC;
```

</Section>

<Section label="Why we need it">

In production machine learning:
- **In-Database Processing at Scale**: Processing petabytes of data inside BigQuery or Snowflake using SQL leverages distributed query engines. Bringing raw unaggregated data into Python memory causes Out-Of-Memory (OOM) crashes.
- **Relational Feature Stores**: Online and offline feature stores (such as Feast or Hopsworks) use SQL queries as foundational definition layers for ML feature tables.
- **Data Quality & Leakage Prevention**: Point-in-time joins in SQL ensure that features constructed for a historical training sample only include information available *before* the prediction timestamp, preventing catastrophic data leakage.

</Section>

### 1. The True SQL Query Execution Order

While SQL queries are *written* starting with `SELECT`, SQL query planners *execute* clauses in a very specific logical order:

```
1. FROM & JOIN     ──> Locate and unite tables
2. WHERE           ──> Filter individual rows
3. GROUP BY        ──> Bucket rows into groups
4. HAVING          ──> Filter aggregated groups
5. SELECT          ──> Select columns and compute expressions/aliases
6. DISTINCT        ──> Eliminate duplicate rows
7. ORDER BY        ──> Sort the resulting rows
8. LIMIT / OFFSET  ──> Slice row pagination
```

<Callout kind="warning">
  Because `WHERE` executes *before* `GROUP BY` and `SELECT`, you **cannot** filter on aggregate functions inside `WHERE` (e.g. `WHERE COUNT(order_id) > 5` will throw a syntax error). Filtering on aggregated metrics must always be placed in the `HAVING` clause!
</Callout>

<Analogy>
  Imagine an international postal sorting facility. First, you gather packages from all delivery vans (**`FROM & JOIN`**). You immediately discard damaged or unaddressed boxes (**`WHERE`**). Next, you sort the remaining packages into destination city bins (**`GROUP BY`**). You then inspect each bin and set aside any city with fewer than 50 parcels (**`HAVING`**). Finally, you stamp tracking barcodes onto the selected items (**`SELECT`**) and line them up from heaviest to lightest (**`ORDER BY`**).
</Analogy>

### 2. Filtering and Conditional Expressions

The `WHERE` clause isolates specific records using logical operators:

| Operator | Syntax Example | Meaning |
| :--- | :--- | :--- |
| **Comparison** | `price >= 100 AND price <= 500` | Value within numeric range |
| **Set Membership** | `device_type IN ('mobile', 'tablet')` | Matches any element in list |
| **Pattern Match** | `email LIKE '%@university.edu'` | Case-sensitive pattern matching |
| **Null Checks** | `churned_date IS NOT NULL` | Checks for present/absent values |
| **Conditional CASE** | `CASE WHEN age < 25 THEN 1 ELSE 0 END` | Creates binary feature flags |

```sql
SELECT 
    customer_id,
    amount,
    CASE 
        WHEN amount > 1000 THEN 'high_value'
        WHEN amount BETWEEN 200 AND 1000 THEN 'medium_value'
        ELSE 'low_value'
    END AS customer_segment
FROM transactions
WHERE status = 'completed' AND amount IS NOT NULL;
```

### 3. Multi-Table Joins: Connecting Feature Entities

Relational schemas normalize data across tables linked by keys (e.g. `user_id`). We use **JOINs** to reassemble feature matrices:

```
        Table A (Users)               Table B (Orders)
  ┌─────────┬──────────────┐    ┌──────────┬─────────┬────────┐
  │ user_id │ signup_date  │    │ order_id │ user_id │ amount │
  ├─────────┼──────────────┤    ├──────────┼─────────┼────────┤
  │    1    │  2024-01-15  │    │   101    │    1    │  50.0  │
  │    2    │  2024-02-01  │    │   102    │    1    │  35.0  │
  │    3    │  2024-03-10  │    │   103    │    4    │  80.0  │
  └─────────┴──────────────┘    └──────────┴─────────┴────────┘
```

- **`INNER JOIN`**: Returns rows only when there is a match in *both* tables (e.g., users who placed orders).
- **`LEFT JOIN`**: Returns *all* rows from Table A, along with matching rows from Table B (unmatched Table B values become `NULL`). Essential in ML feature engineering so that users with zero purchases are retained (and later imputed with 0).
- **`RIGHT JOIN`**: Returns all rows from Table B, matching Table A.
- **`FULL OUTER JOIN`**: Returns all records when there is a match in either table.

```sql
-- LEFT JOIN ensures inactive users are not dropped from feature matrix:
SELECT 
    u.user_id,
    u.signup_date,
    COALESCE(SUM(o.amount), 0.0) AS total_spent
FROM users u
LEFT JOIN orders o 
    ON u.user_id = o.user_id
GROUP BY u.user_id, u.signup_date;
```

### 4. Aggregations with `GROUP BY` and `HAVING`

The **Split-Apply-Combine** pattern aggregates multiple row observations per group into singular statistical summaries:

```sql
SELECT 
    merchant_category,
    COUNT(*) AS total_transactions,
    ROUND(AVG(transaction_amount), 2) AS mean_amount,
    ROUND(STDDEV(transaction_amount), 2) AS std_amount,
    MAX(transaction_amount) AS max_single_transaction
FROM card_transactions
GROUP BY merchant_category
HAVING COUNT(*) >= 1000;
```

### 5. Advanced Feature Engineering: Common Table Expressions (CTEs) & Window Functions

#### Common Table Expressions (`WITH ... AS`)
CTEs make complex queries readable and maintainable by decomposing logic into sequential named steps:

```sql
WITH user_aggregates AS (
    SELECT 
        user_id,
        AVG(session_duration_sec) AS avg_duration
    FROM user_sessions
    GROUP BY user_id
)
SELECT 
    u.user_id,
    u.subscription_tier,
    a.avg_duration
FROM users u
JOIN user_aggregates a ON u.user_id = a.user_id;
```

#### Window Functions for Sequential ML Features
Unlike `GROUP BY`, which collapses rows into a single summary, **Window Functions** compute aggregate or positional metrics across rows while **retaining individual row identity**:

```sql
-- Calculate user transaction order sequence and recency lag features:
SELECT 
    user_id,
    order_id,
    order_date,
    amount,
    -- Rank each purchase sequentially per user:
    ROW_NUMBER() OVER (
        PARTITION BY user_id 
        ORDER BY order_date ASC
    ) AS purchase_sequence_number,
    -- Fetch the amount of the previous purchase:
    LAG(amount, 1) OVER (
        PARTITION BY user_id 
        ORDER BY order_date ASC
    ) AS previous_order_amount
FROM orders;
```

Window functions are indispensable in temporal machine learning for building lag variables, calculating rolling customer spend, and preparing sequence models.
