<Section label="What is it?">

**Machine Learning Project Structuring** is the software engineering discipline of organizing code, data, configuration, models, and experimentation artifacts into a modular, clean, and reproducible codebase.

Unlike traditional software engineering where only source code is tracked, machine learning systems depend on a three-way coupling:
1. **Source Code**: Preprocessing logic, model architectures, training routines, and evaluation metrics.
2. **Data Assets**: Raw observations, cleaned tables, feature matrices, and training splits.
3. **Model Artifacts**: Serialized weights (`.pt`, `.onnx`, `.joblib`), tokenizer files, and hyperparameter configuration logs.

A disciplined repository layout separates these concerns cleanly, preventing code bloat, data corruption, and "works on my machine" failures.

</Section>

<Section label="Why we need it">

In amateur data science projects, researchers often work in a single messy directory containing 20 untitled notebooks, hardcoded file paths (`/Users/alice/Desktop/data.csv`), mixed dependencies, and untracked scripts. 

Adopting a standardized repository structure provides:
- **Flawless Reproducibility**: Any team member or automated CI pipeline can clone the repository, install dependencies in one command, and reproduce the exact model metrics.
- **Clear Code vs. Data Boundaries**: Prevents accidentally committing confidential customer data or multi-gigabyte weight files into Git history.
- **Notebook-to-Production Transition**: Keeps exploratory notebooks for prototyping while moving tested, reusable logic into clean Python modules (`src/`) that can be packaged and deployed as microservices.
- **Decoupled Hyperparameters**: Decouples model definitions from training configurations (learning rates, batch sizes, epochs), allowing sweeping experiments without touching codebase logic.

</Section>

### 1. The Industry Standard ML Repository Layout

The most widely adopted architecture in industry is the **Cookiecutter Data Science** pattern:

```
ml-project/
├── data/
│   ├── raw/             # Immutable original data (read-only!)
│   ├── interim/         # Intermediate transformed features
│   └── processed/       # Final training-ready splits (train.parquet, test.parquet)
├── notebooks/           # Exploratory Jupyter notebooks (numbered sequentially)
│   ├── 01_data_exploration.ipynb
│   └── 02_model_baseline.ipynb
├── src/                 # Reusable, testable source code modules
│   ├── __init__.py
│   ├── data/            # Ingestion and cleaning scripts
│   ├── features/        # Feature transformers and encoders
│   ├── models/          # Model architecture, training, and inference logic
│   └── visualization/   # Diagnostic plots and reporting charts
├── configs/             # Declarative configuration files (YAML, JSON)
│   ├── base_config.yaml
│   └── resnet_experiment.yaml
├── models/              # Serialized model checkpoints and artifacts (local only)
├── tests/               # Unit and integration tests (pytest)
├── .gitignore           # Explicit exclusion rules for data, caches, and weights
├── requirements.txt     # Pinned Python package dependencies
├── pyproject.toml       # Modern package metadata and build configuration
└── README.md            # Project overview, setup steps, and execution instructions
```

<Analogy>
  Think of a machine learning repository like a Michelin-starred commercial kitchen. The **`data/raw/`** is the cold storage pantry where fresh ingredients sit untouched in their original state. The **`src/`** is the set of standardized chef knives and cookware (reusable code). The **`notebooks/`** is the chef's scratchpad for testing experimental flavor combinations. And the **`configs/`** is the exact printed recipe card detailing oven temperature and cooking time.
</Analogy>

### 2. The Golden Rules of Data and Model Hygiene

1. **`data/raw/` is Strictly Read-Only**: Never edit raw data files in place. If data requires cleaning or missing value imputation, write a script that reads from `data/raw/` and outputs new files into `data/interim/` or `data/processed/`.
2. **Never Hardcode File Paths**: Use Python's `pathlib.Path` or project-relative anchors rather than absolute OS paths:

```python
# ❌ Dangerous and unportable:
data_path = "/Users/developer/Desktop/projects/ml-app/data/raw/train.csv"

# ✅ Portable across macOS, Linux, and Windows:
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent
data_path = BASE_DIR / "data" / "raw" / "train.csv"
```

### 3. Mastering `.gitignore` for Machine Learning

Git is designed for tracking lightweight, text-based code diffs. Committing large binary files (like datasets or neural network checkpoints) permanently bloats the `.git` directory, causing clone operations to crawl or fail.

Every ML repository should feature an explicit `.gitignore`:

```gitignore
# Byte-compiled / optimized Python files
__pycache__/
*.py[cod]
*$py.class

# Virtual environments
.venv/
venv/
env/

# Environment variables and API keys
.env
*.pem
credentials.json

# Raw and processed datasets (Use DVC or cloud storage instead)
data/raw/*
data/interim/*
data/processed/*
!data/raw/.gitkeep

# Model weights and serialized checkpoints
models/*.pt
models/*.pth
models/*.bin
models/*.onnx
models/*.joblib

# Jupyter Notebook checkpoints and caches
.ipynb_checkpoints/
.pytest_cache/
.coverage
```

<Callout kind="tip">
  To version large datasets (e.g. 50GB images) and model checkpoints, use dedicated tools like **DVC (Data Version Control)** or store them in S3/GCS buckets with cryptographic checksums, committing only small pointer files into Git.
</Callout>

### 4. Dependency Management: `requirements.txt` vs. `pyproject.toml`

To ensure deterministic reproduction across team members and deployment containers:

```bash
# 1. Classical approach: Pinning exact package versions
# requirements.txt
torch==2.4.0
scikit-learn==1.5.1
pandas==2.2.2
pydantic==2.8.2
pytest==8.3.2

# Install exactly matching environments
pip install -r requirements.txt
```

In modern Python engineering, tools like **Poetry**, **UV**, or **Hatch** use `pyproject.toml` combined with a cryptographic lockfile (`poetry.lock` or `uv.lock`) to resolve transitive dependency trees deterministically.

### 5. Decoupling Pipelines: Configs and Scripts

Do not embed hyperparameters directly into training routines. Use declarative configuration files:

```yaml
# configs/train_config.yaml
dataset:
  train_path: "data/processed/train.parquet"
  batch_size: 64
  num_workers: 4

training:
  epochs: 50
  learning_rate: 0.001
  weight_decay: 0.01
  model_type: "resnet50"
```

Then load the configuration inside a modular `train.py`:

```python
# train.py
import yaml
import argparse
from pathlib import Path

def parse_args():
    parser = argparse.ArgumentParser(description="Train ML Model")
    parser.add_argument("--config", type=str, default="configs/train_config.yaml")
    return parser.parse_args()

def main():
    args = parse_args()
    with open(args.config, "r") as f:
        config = yaml.safe_load(f)

    print(f"Loading data from: {config['dataset']['train_path']}")
    print(f"Training for {config['training']['epochs']} epochs at LR={config['training']['learning_rate']}")

if __name__ == "__main__":
    main()
```

This decoupled pattern enables running distributed hyperparameter sweeps across different config files (`python train.py --config configs/exp1.yaml`) without modifying a single line of application source code.
