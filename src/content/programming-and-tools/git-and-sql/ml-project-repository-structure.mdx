<Section label="What is it?">

**Machine Learning Project Structuring** is the software engineering discipline of organizing source code, raw data pipelines, hyperparameter configurations, trained model artifacts, and evaluation metrics into a modular, standardized, and auditable repository.

Unlike standard web applications where the software behavior is entirely determined by lines of code, machine learning systems exhibit **joint dependency** across three distinct dimensions:
1. **Codebase Logic**: Preprocessing routines, data transformers, neural network backbones, and loss functions.
2. **Data Pipeline Assets**: Raw observations, intermediate features, train/val/test splits, and data schemas.
3. **Model Artifacts & Checkpoints**: Serialized weights (`.pt`, `.safetensors`, `.onnx`), tokenizer states, scalers, and evaluation metric logs.

Without a rigorous repository structure, ML projects quickly devolve into what Google researchers famously described as the *"Hidden Technical Debt in Machine Learning Systems"*: messy directories of unversioned notebooks, hardcoded local file paths, irreproducible hyperparameters, and silent data leakage.

</Section>

<Section label="Why we need it">

In research and industrial environments:
- **Instant Developer Onboarding**: When a new data scientist joins a team, a standard directory hierarchy means they immediately know where data is loaded (`src/data/`), where features are calculated (`src/features/`), and where configurations are defined (`configs/`).
- **Eliminating "Works On My Machine" Failures**: Disentangling code from local paths (`/Users/bob/data.csv`) and pinning dependencies guarantees that training scripts run identically on a local MacBook, a cloud GPU cluster (AWS EC2 / GCP Compute Engine), or an automated CI/CD container.
- **Clean Transition from Prototyping to Production**: Data scientists prototype freely inside numbered Jupyter notebooks (`01_eda.ipynb`), while reusable classes and training logic are extracted into testable, packaged Python modules (`src/`).
- **Data Governance and Security**: Raw customer datasets, PII (Personally Identifiable Information), and secret API tokens are strictly quarantined from entering version control.

</Section>

### 1. Enterprise Directory Hierarchy: The Cookiecutter ML Pattern

The most widely adopted standard across top tech teams is an evolved version of the **Cookiecutter Data Science** pattern:

```
ml-project/
├── data/                            # Hierarchical Medallion data store
│   ├── raw/                         # Bronze tier: Immutable original data dumps
│   ├── interim/                     # Silver tier: Cleansed, joined, validated tables
│   └── processed/                   # Gold tier: Final feature matrices & splits
├── notebooks/                       # Exploratory analysis & scratchpads
│   ├── 01_exploratory_data_analysis.ipynb
│   ├── 02_feature_selection.ipynb
│   └── 03_baseline_model_evaluation.ipynb
├── src/                             # Reusable production package
│   ├── __init__.py
│   ├── data/                        # Ingestion, validation, and split utilities
│   │   ├── make_dataset.py
│   │   └── data_validation.py
│   ├── features/                    # Feature transformations & scalers
│   │   └── build_features.py
│   ├── models/                      # Model architectures & training routines
│   │   ├── architectures.py
│   │   ├── train.py
│   │   └── predict.py
│   └── utils/                       # Logging, seed fixing, and I/O helpers
│       └── helpers.py
├── configs/                         # Declarative hyperparameter configurations
│   ├── config.yaml
│   └── experiment/
│       ├── exp1_resnet.yaml
│       └── exp2_vit.yaml
├── models/                          # Serialized weights & checkpoints (local only)
│   └── checkpoints/
├── tests/                           # Automated unit and integration tests (pytest)
│   ├── test_data_pipeline.py
│   └── test_model_inference.py
├── Dockerfile                       # Multi-stage production container definition
├── .dockerignore                    # Prevents bloated images
├── .gitignore                       # Explicit exclusion rules for data and weights
├── requirements.txt                 # Classical pip dependency specification
├── pyproject.toml                   # Modern Python build specification (Poetry/UV)
└── README.md                        # Documentation: setup, training, and API usage
```

<Analogy>
  Think of an enterprise ML repository like an automated pharmaceutical laboratory:
  - **`data/raw/` (Bronze)** is the sealed biological sample cold storage. Nobody alters raw samples directly.
  - **`data/processed/` (Gold)** is the purified, sterilized compound ready for testing.
  - **`src/`** is the sterile robotic equipment calibrated to handle, measure, and analyze compounds identically every time.
  - **`notebooks/`** is the researcher’s personal lab journal for quick brainstorming.
  - **`configs/`** is the exact printed formula specifying chemical proportions, incubation temperatures, and duration.
</Analogy>

### 2. The Medallion Data Tier Architecture

Modern ML data pipelines adopt the **Medallion Data Architecture**:

| Tier | Folder | Format | Immutability | Purpose |
| :--- | :--- | :--- | :--- | :--- |
| **Bronze** | `data/raw/` | Raw JSON / CSV / Parquet | Strictly Read-Only | Pristine original source of truth from database dumps or APIs. |
| **Silver** | `data/interim/` | Partitioned Parquet | Reproducible | Cleansed data: nulls handled, dates parsed, tables joined. |
| **Gold** | `data/processed/` | Scaled Parquet / NumPy | Reproducible | Final feature matrices, normalized tensors, train/val/test splits. |

<Callout kind="warning">
  **The Immutability Law of Raw Data**: Never edit raw data files in place. If an anomaly is discovered in `data/raw/sales.csv`, write code in `src/data/make_dataset.py` to filter or repair the record into `data/interim/`. If your raw data is altered manually, all downstream feature engineering loses its reproducibility.
</Callout>

### 3. Path Management: Eliminating Hardcoded Absolute Paths

Hardcoded absolute paths (`/Users/hamim/Desktop/data.csv`) break when executed on another machine, inside a Docker container, or in CI/CD pipelines.

Always resolve paths dynamically relative to the repository root using Python's modern `pathlib`:

```python
# src/utils/paths.py
from pathlib import Path

# Anchor to the project root directory (two levels up from src/utils/)
PROJECT_ROOT = Path(__file__).resolve().parents[2]

DATA_DIR = PROJECT_ROOT / "data"
RAW_DATA_DIR = DATA_DIR / "raw"
PROCESSED_DATA_DIR = DATA_DIR / "processed"
CONFIGS_DIR = PROJECT_ROOT / "configs"
MODELS_DIR = PROJECT_ROOT / "models"

# Safe usage in your pipeline:
def load_training_features():
    feature_path = PROCESSED_DATA_DIR / "train_features.parquet"

        raise FileNotFoundError(f"Feature matrix missing at {feature_path}. Run build_features.py first.")
    return pd.read_parquet(feature_path)
```

### 4. Model Artifact Formats: Choosing the Right Serialization

Serializing trained models correctly is vital for cross-platform portability and security:

| Format | Extension | Library | Security / Pros & Cons |
| :--- | :---: | :--- | :--- |
| **PyTorch State Dict** | `.pt` / `.pth` | PyTorch | Native Python dictionary of layer tensors. Requires model class code to reload. Uses Python `pickle` (security vulnerability if untrusted). |
| **SafeTensors** | `.safetensors` | Hugging Face | Zero-copy deserialization, lightning fast, and **immune to arbitrary code execution attacks** (no `pickle`). Current industry standard for LLMs and Diffusion models. |
| **ONNX** | `.onnx` | ONNX Runtime | Open Neural Network Exchange. Cross-language (Python, C++, Java, Rust). Runs blazingly fast on CPUs and GPUs with zero Python dependency in production! |
| **Joblib / Pickle** | `.joblib` | Scikit-learn | Standard for classical tabular models (Random Forests, Gradient Boosting, Scalers). Caution: never load untrusted `.pkl` files. |

```python
# Example: Saving weights securely with SafeTensors
from safetensors.torch import save_file, load_file

# Saving model weights:
tensors = {k: v.cpu() for k, v in model.state_dict().items()}
save_file(tensors, "models/checkpoints/resnet50_epoch20.safetensors")

# Loading securely:
loaded_tensors = load_file("models/checkpoints/resnet50_epoch20.safetensors")
model.load_state_dict(loaded_tensors)
```

### 5. Type-Safe Configuration Management with Pydantic and YAML

Hardcoding hyperparameters inside Python code makes sweeping experiments difficult. However, reading plain raw YAML dictionaries often causes silent bugs if a key is misspelled (e.g., `cfg["learning_ratee"]` returns `None` instead of throwing an error).

Best practice: Parse YAML configurations through a strict, type-safe **Pydantic schema**:

```yaml
# configs/experiment_baseline.yaml
experiment_name: "resnet50_cifar100"
seed: 42

data:
  batch_size: 64
  num_workers: 4
  val_split: 0.2

model:
  architecture: "resnet50"
  learning_rate: 0.001
  weight_decay: 0.0001
  epochs: 50
```

```python
# src/config_schema.py
from pydantic import BaseModel, PositiveInt, PositiveFloat, Field
import yaml

class DataConfig(BaseModel):
    batch_size: PositiveInt = Field(default=32)
    num_workers: int = Field(default=2, ge=0)
    val_split: float = Field(default=0.2, gt=0.0, lt=1.0)

class ModelConfig(BaseModel):
    architecture: str
    learning_rate: PositiveFloat
    weight_decay: float = Field(default=0.0, ge=0.0)
    epochs: PositiveInt

class ExperimentConfig(BaseModel):
    experiment_name: str
    seed: int = 42
    data: DataConfig
    model: ModelConfig

def load_config(config_path: str) -> ExperimentConfig:
    with open(config_path, "r") as f:
        raw_dict = yaml.safe_load(f)
    # Pydantic validates types and value ranges immediately:
    return ExperimentConfig(**raw_dict)
```

If an engineer accidentally inputs `learning_rate: -0.01` or `epochs: 0`, Pydantic halts execution with an explicit error before any expensive training cluster resources are wasted!

### 6. Production Containerization: Multi-Stage Dockerfile for ML

To eliminate OS-level dependency mismatches between local macOS development and cloud Linux GPU instances, encapsulate your application in a **Multi-Stage Dockerfile**:

```dockerfile
# Stage 1: Build & compilation environment
FROM python:3.11-slim AS builder

WORKDIR /build
RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential \
    curl \
    && rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

# Stage 2: Minimal, lean production runtime
FROM python:3.11-slim AS runner

WORKDIR /app

# Create a non-root security user
RUN groupadd -r mluser && useradd -r -g mluser mluser

# Copy installed Python packages from builder stage
COPY --from=builder /root/.local /home/mluser/.local
ENV PATH=/home/mluser/.local/bin:$PATH

# Copy application code
COPY src/ /app/src/
COPY configs/ /app/configs/

USER mluser
EXPOSE 8000

# Run production inference API
CMD ["uvicorn", "src.api:app", "--host", "0.0.0.0", "--port", "8000"]
```

Multi-stage builds reduce final Docker image sizes by up to 70%, eliminating C++ build tools, speeding up Kubernetes deployment rollouts, and closing security attack vectors.
