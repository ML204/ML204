<Section label="What is it?">

**Git** is a distributed, content-addressed version control system designed to record immutable snapshots of a project's filesystem over time. Unlike legacy centralized version control systems (such as SVN or CVS) that track file-by-file differences (delta-based versioning), Git captures the entire state of your project as a cryptographic graph of snapshot nodes called **commits**.

At its architectural foundation:
- **Working Directory**: The active directory on your local filesystem where code, notebooks, and configuration files are edited.
- **Staging Area (Index)**: A binary cache file (`.git/index`) acting as a preparatory scratchpad where changes are queued, inspected, and vetted before being recorded into permanent history.
- **Local Repository**: The internal `.git` object database containing all compressed historical blobs, directory trees, commit metadata, and branch pointers (`HEAD`).
- **Remote Repository**: A centralized server (such as GitHub, GitLab, or Hugging Face) serving as the authoritative synchronization hub for team collaboration, peer reviews, and automated CI/CD evaluation pipelines.

```
Working Directory  ──(git add)──>  Staging Area (Index)  ──(git commit)──>  Local Repo (.git)  ──(git push)──>  Remote (GitHub)
       │                                                                           ▲
       └───────────────────────────────(git commit -a)─────────────────────────────┘
```

</Section>

<Section label="Why we need it">

In modern machine learning engineering, version control is the backbone of scientific reproducibility:

1. **The Three-Way Reproducibility Triangle**:
   A machine learning model cannot be reproduced by code alone. Training output depends on:
   - **Code State**: The exact preprocessing scripts, model architecture definitions, and loss functions (tracked via Git commit SHAs).
   - **Data State**: The exact version and checksum of training and validation datasets (tracked via Git LFS, DVC, or S3 bucket versioning).
   - **Environment State**: The exact library versions, CUDA drivers, and hyperparameters (tracked via lockfiles and Docker container tags).
   By logging the active Git commit hash directly into experiment trackers (such as MLflow, Weights & Biases, or Comet ML), any production model deployed years later can be traced back to the exact line of code that produced it.

2. **Isolated Scientific Exploration**:
   Machine learning development is non-linear and hypothesis-driven. Researchers routinely explore divergent model backbones (e.g., Vision Transformers vs. ConvNeXt) or loss formulations (Focal Loss vs. Cross-Entropy). Git branching allows multiple researchers to iterate simultaneously on isolated branches without clobbering baseline scripts or interfering with colleague runs.

3. **Risk Mitigation and Zero-Downtime Rollbacks**:
   When an experimental data normalization bug causes numerical instability or model divergence in production, Git allows instantaneous time travel to any historically verified, stable release tag (`git checkout tags/v1.2.0`).

4. **Auditable Peer Review**:
   Through Pull Requests (PRs), teams conduct rigorous code reviews to identify subtle data leakage bugs, unvectorized slow loops, and missing unit tests before code ever touches production training clusters.

</Section>

### 1. Git Internals: The Directed Acyclic Graph (DAG) and Object Store

Beneath the CLI commands, Git is fundamentally a simple content-addressed key-value database stored inside the `.git/objects/` folder. Every piece of data is hashed using SHA-1 (or SHA-256 in newer configurations) to produce a unique 40-character hexadecimal identifier.

Git represents your codebase using four primitive object types:
1. **Blob (Binary Large Object)**: Stores raw file content without filenames or directory hierarchies. Two identical files with different names point to the exact same blob in memory.
2. **Tree**: Represents a directory. It maps filenames and permissions to their corresponding blob hashes or sub-tree hashes.
3. **Commit**: A permanent snapshot record that points to a root Tree object. It includes metadata: author, committer, timestamp, commit message, and parent commit hashes.
4. **Annotated Tag**: A permanent pointer tied to a specific commit hash, storing tagger name, GPG cryptographic signatures, and release notes.

Because every commit references the cryptographic hash of its parent commits, Git history forms an immutable **Directed Acyclic Graph (DAG)**. Modifying even a single character in a two-year-old commit alters that commit's hash, which cascades and alters every subsequent descendant hash, making silent history tampering mathematically impossible.

```
[Commit A] <── [Commit B] <── [Commit C] <── (HEAD -> main)
     │              │              │
  (Tree)         (Tree)         (Tree)
     │              │              │
  [Blobs]        [Blobs]        [Blobs]
```

### 2. The Four Stages and Daily Development Workflow

Every tracked file in a Git repository moves through a defined lifecycle:

| File Status | Working Directory | Staging Area | Local Repository | Remote Repository |
| :--- | :---: | :---: | :---: | :---: |
| **Untracked** | File exists | Not staged | Absent | Absent |
| **Modified** | Changed on disk | Stale version | Old snapshot | Old snapshot |
| **Staged** | Staged for commit | New version | Old snapshot | Old snapshot |
| **Committed** | Matches repo | Matches repo | Current snapshot | Old snapshot |
| **Pushed** | Synchronized | Synchronized | Current snapshot | Synchronized |

```bash
# 1. Initialize a new local repository
git init

# 2. Inspect active branch, staged files, and untracked changes
git status

# 3. Stage changes specifically (avoid indiscriminate 'git add .')
git add train.py src/models/transformer.py

# 4. Record a snapshot with an imperative, conventional commit message
git commit -m "feat(model): implement rotary positional embeddings (RoPE)"

# 5. Connect local repo to remote host and push main branch
git remote add origin https://github.com/organization/ml-platform.git
git push -u origin main
```

<Callout kind="tip">
  Follow the **Conventional Commits** specification (`feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`). Structured commit histories make automated semantic versioning, changelog generation, and historical auditing effortless.
</Callout>

<Analogy>
  Think of Git like a photography studio with a darkroom.
  - The **Working Directory** is the open stage where actors, lighting, and camera equipment are arranged and modified continuously.
  - The **Staging Area** is the camera viewfinder. You choose which actors and props to frame for the upcoming photo.
  - The **Commit** is pressing the camera shutter: an instantaneous, permanent photographic negative saved into the studio archive with a timestamp.
  - **Pushing** is publishing the developed photograph to an international art gallery where your collaborators can inspect it.
</Analogy>

### 3. Inspecting Diffs, History, and the `HEAD` Pointer

`HEAD` is a special pointer file (`.git/HEAD`) that references the currently checked-out branch or commit. Knowing how to query `HEAD` and diffs is essential:

```bash
# Compare unstaged working directory changes against the staging area
git diff

# Compare staged changes against the latest commit (HEAD)
git diff --staged

# Compare changes between two branches
git diff main..experiment/focal-loss

# Display a compact, colorized visual graph of commit history
git log --oneline --graph --decorate --all -n 15

# View the exact code changes introduced by a specific commit
git show 3f619f4
```

#### The Detached `HEAD` State
When you check out an arbitrary commit hash directly rather than a branch name (`git checkout 3f619f4`), your repository enters a **Detached HEAD** state. Any new commits made in this state belong to no branch; when you switch back to `main`, orphaned commits are eventually swept away by Git's Garbage Collector (`git gc`). To save work done in a detached state, simply create a branch from it: `git switch -c recovery-branch`.

### 4. Branching, Merging, and Conflict Resolution

Branches in Git are merely 41-byte text files in `.git/refs/heads/` containing a commit hash. Creating or deleting a branch takes less than a millisecond and consumes negligible disk space.

```bash
# Modern command to create and switch to a new branch in one command:
git switch -c feature/focal-loss

# Make modifications, stage, and commit
git add src/loss.py
git commit -m "feat(loss): add alpha-balanced focal loss for class imbalance"

# Switch back to main
git switch main
```

#### Fast-Forward vs. Three-Way Merge
- **Fast-Forward Merge**: If `main` has zero new commits since `feature/focal-loss` was branched, Git simply slides the `main` label pointer forward to the tip of `feature/focal-loss`. No new commit object is created.
- **Three-Way Merge**: If both `main` and `feature/focal-loss` have received independent commits, Git locates their **Lowest Common Ancestor (LCA)** commit, analyzes changes from both branches, and constructs a new **Merge Commit** containing two parent pointers.

```
Fast-Forward:
[A] ──> [B] ──> [C] (main, feature)

Three-Way Merge:
[A] ──> [B] ─────────────> [Merge Commit M] (main)
         └──> [C] ──> [D] ────────┘ (feature)
```

#### Merge Conflicts and Resolution
A conflict arises when two branches modify the **exact same lines of a file** concurrently:

```python
# Conflicted src/train.py:
<<<<<<< HEAD
# Changes currently on main:
learning_rate = 1e-4
optimizer = torch.optim.AdamW(model.parameters(), lr=learning_rate, weight_decay=1e-2)
=======
# Incoming changes from experiment/optimizer branch:
learning_rate = 5e-4
optimizer = torch.optim.Adam(model.parameters(), lr=learning_rate, eps=1e-8)
>>>>>>> experiment/optimizer
```

**Conflict Resolution Protocol**:
1. Open the file in your code editor.
2. Carefully inspect the logic between `<<<<<<< HEAD` (current branch), `=======` (separator), and `>>>>>>> <branch>` (incoming branch).
3. Determine the correct production behavior (e.g., combining settings or adopting the validated hyperparameter).
4. Delete all conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`).
5. Stage the resolved file: `git add src/train.py`.
6. Finalize the merge: `git commit` (leave the auto-generated merge message).

### 5. Advanced Git Operations for Machine Learning

#### Git Stash: Shelving Unfinished Work
When an urgent bug occurs in production while you are halfway through training script modifications:
```bash
# Stash uncommitted changes (both staged and unstaged)
git stash save "wip: transformer layer norm experiment"

# Working directory is now completely clean; switch and fix production bug
git switch main
# ... fix bug, commit, push ...

# Return to your experiment branch and restore work
git switch feature/transformer
git stash pop
```

#### Git Rebase: Maintaining a Pristine Linear History
Unlike `git merge`, which introduces non-linear merge bubbles, `git rebase` replays your branch commits on top of the latest `main`:
```bash
git switch feature/transformer
git rebase main
```
<Callout kind="warning">
  **The Golden Rule of Rebasing**: Never rebase commits that have already been pushed to a shared public remote branch! Rebasing rewrites commit hashes; doing so forces collaborators into divergent history nightmares. Only rebase local, unshared feature branches.
</Callout>

#### Git Cherry-Pick: Surgical Commit Extraction
If a colleague implemented a critical gradient clipping bugfix on a giant, unready branch `experiment/large-scale-nlp`, you can pluck that single commit into your branch without merging their unfinished features:
```bash
git cherry-pick a8f41c2
```

### 6. Git LFS and Quality Gates with Pre-Commit Hooks

#### Git LFS (Large File Storage)
Git struggles with large binary files (weights, audio datasets, video clips). Committing a 2GB `.pt` file means every team member must download that 2GB blob every time they clone the repo, even if that file was deleted five commits later.

**Git LFS** solves this by storing tiny text pointer files (~130 bytes) inside Git, while streaming the multi-gigabyte binary payload to a specialized object store:

```bash
# 1. Install Git LFS extension
git lfs install

# 2. Track large machine learning model formats
git lfs track "*.pt"
git lfs track "*.onnx"
git lfs track "*.safetensors"
git lfs track "data/raw/*.parquet"

# 3. Commit the generated .gitattributes file
git add .gitattributes
git commit -m "chore(lfs): track binary model checkpoints and parquet files"
```

#### Pre-Commit Quality Gates
To prevent team members from accidentally committing secrets (`API_KEY="sk-..."`), poorly formatted code, or heavy unstripped Jupyter Notebook cell outputs:

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: check-added-large-files
        args: ['--maxkb=500']  # Blocks any file > 500KB not in LFS!
      - id: detect-private-key
      - id: check-yaml
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.5.5
    hooks:
      - id: ruff
        args: [--fix]
  - repo: https://github.com/kynan/nbstripout
    rev: 0.7.1
    hooks:
      - id: nbstripout         # Strips heavy outputs and execution counts from .ipynb
```

Install the hook once via `pre-commit install`. Git will automatically execute these sanity checks before allowing any commit to register!
