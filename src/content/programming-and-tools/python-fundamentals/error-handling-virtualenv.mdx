<Section label="What is it?">

Writing production-grade machine learning software requires two critical disciplines:
1. **Defensive Error Handling**: Utilizing `try`, `except`, `else`, and `finally` to gracefully catch and resolve runtime anomalies (such as corrupt dataset rows, GPU Out-Of-Memory spikes, or missing checkpoints) without corrupting training runs.
2. **Environment Isolation**: Managing isolated Python runtimes using virtual environments (`venv`) and dependency pinning (`requirements.txt`), ensuring that packages installed for one project never collide with another.

### The Python Exception Hierarchy

```text
BaseException
 ├── SystemExit                   # Raised by sys.exit()
 ├── KeyboardInterrupt            # Triggered when user presses Ctrl+C
 └── Exception                    # Base class for all standard runtime errors!
      ├── ArithmeticError
      │    └── ZeroDivisionError
      ├── LookupError
      │    ├── IndexError         # List index out of bounds
      │    └── KeyError           # Missing dictionary key
      ├── ValueError              # Correct type, invalid value (e.g. negative LR)
      ├── TypeError               # Operation applied to inappropriate type
      └── OSError
           └── FileNotFoundError  # Missing dataset or checkpoint file
```

<Callout kind="warning">
  **Why You Must Never Write Bare `except:`:**
  Catching bare `except:` or `except BaseException:` intercepts `KeyboardInterrupt` and `SystemExit`. If your training script enters an infinite loop, pressing `Ctrl+C` will be intercepted and ignored, making it impossible to stop the process without killing the terminal! Always catch `except Exception:` or specific error subclasses.
</Callout>

</Section>

<Section label="Why we need it">

In production machine learning:
- **Protecting Multi-Day Training Runs**: If a dataset contains 1 corrupt image out of 5,000,000, an unhandled error crashes a multi-thousand-dollar training run on day 3. Proper exception handling logs the corrupt file path and continues training.
- **Defensive Input Validation**: Raising descriptive custom exceptions (`DimensionMismatchError: Expected feature size 128, but received 64`) prevents silent dimensional bugs caused by unintended NumPy array broadcasting.
- **Dependency Hell Prevention**: Project A might require PyTorch 2.0 with CUDA 11.8, while Project B requires PyTorch 2.5 with CUDA 12.4. Without virtual environments, installing one overwrites the other and breaks both projects.

</Section>

### 1. The Full Lifecycle of `try` / `except` / `else` / `finally`

Python provides a complete four-part control structure for defensive programming:

```python
def load_checkpoint(checkpoint_path: str):
    file_handle = None
    try:
        print(f"Attempting to load checkpoint from: {checkpoint_path}")
        file_handle = open(checkpoint_path, "r", encoding="utf-8")
        weights = [float(x) for x in file_handle.read().split(",")]

    except FileNotFoundError:
        # 1. Handles missing files specifically
        print("Warning: Checkpoint missing! Initializing random weights.")
        weights = [0.01, -0.02, 0.05]

    except ValueError as err:
        # 2. Handles non-numeric data corrupted on disk
        print(f"Data corruption error: {err}")
        weights = []

    else:
        # 3. Runs ONLY if NO exception was raised in the try block!
        print("Checkpoint successfully loaded and validated.")

    finally:
        # 4. ALWAYS runs regardless of success, error, or early return
        if file_handle is not None and not file_handle.closed:
            file_handle.close()
            print("Checkpoint file descriptor safely closed.")

    return weights
```

<Analogy>
  Think of a `try-except` block as an emergency landing protocol on an aircraft. The `try` block is standard flight. The `except` block is deploying landing gear and emergency slides if an engine fails. The `else` block is taxiing smoothly to the gate when there is no turbulence. The `finally` block is the cabin crew running the post-flight security checklist: it happens every single time, whether the flight was smooth or an emergency landing took place.
</Analogy>

### 2. Creating Custom Exceptions for ML Pipelines

Subclassing Python's built-in `Exception` creates clear, domain-specific error classes for machine learning frameworks:

```python
class MLError(Exception):
    """Base class for all machine learning pipeline errors."""
    pass

class DimensionMismatchError(MLError):
    """Raised when tensor or matrix dimensions fail compatibility checks."""
    def __init__(self, expected_dim: int, actual_dim: int, layer_name: str):
        super().__init__(
            f"[{layer_name}] Expected input dimension {expected_dim}, "
            f"but received tensor with dimension {actual_dim}."
        )

class DivergenceError(MLError):
    """Raised when training loss produces NaN or explodes toward infinity."""
    pass
```

```python
# Enforcing invariants inside a neural network layer:
def forward_pass(input_features, weights):
    if len(input_features) != len(weights):
        raise DimensionMismatchError(
            expected_dim=len(weights),
            actual_dim=len(input_features),
            layer_name="LinearProjection"
        )
```

#### Exception Chaining (`raise ... from`)
When wrapping lower-level I/O errors inside high-level pipeline errors, use `raise ... from` to preserve the original traceback for debugging:

```python
def load_dataset_metadata(path: str):
    try:
        with open(path, "r", encoding="utf-8") as f:
            return f.read()
    except OSError as original_error:
        raise MLError(f"Failed to load dataset at {path}") from original_error
```

### 3. Assertions vs Runtime Exceptions

The `assert condition, "Error message"` statement tests internal assumptions:

```python
# Good use of assert: verifying internal invariants during development
assert learning_rate > 0, "Learning rate must be positive"
```

<Callout kind="warning">
  **Never Use `assert` for Critical Data Validation!**
  When Python is run with the `-O` (optimize) flag (`python -O train.py`), **all assert statements are completely stripped from compiled bytecode!** If you use `assert` to validate user input or dataset integrity, those checks will disappear in production. Always use `if not condition: raise ValueError(...)` for data validation.
</Callout>

### 4. Professional Logging vs Raw `print()`

Raw `print()` statements cannot be filtered, do not capture timestamps, and mix debug outputs with actual program results. Production ML uses Python's standard `logging` module:

```python
import logging

# Configure unified logging format with timestamp and severity level:
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
    handlers=[
        logging.StreamHandler(),                  # Console output
        logging.FileHandler("training.log")       # Persistent disk file
    ]
)

logging.debug("Evaluating step 140...")          # Hidden in INFO mode
logging.info("Epoch 5/10 — Loss: 0.284")          # Standard training log
logging.warning("Learning rate decaying to 1e-4") # Warning event
logging.error("Batch 42 contained corrupt NaN")   # Handled failure
```

### 5. Virtual Environments: What Happens Under the Hood

When you execute Python, the operating system looks up libraries in `sys.path`. Without isolation, all packages are installed globally in `/usr/lib/python3.x/site-packages`.

When you create a virtual environment using `python3 -m venv .venv`:
1. It creates an isolated directory structure containing `bin/` (or `Scripts/` on Windows) and `lib/`.
2. It writes a file named `pyvenv.cfg` pointing to the underlying Python binary.
3. When activated (`source .venv/bin/activate`), it prepends `.venv/bin` to your system `PATH`.
4. Python now installs and resolves packages inside `.venv/lib/python3.x/site-packages`!

```bash
# 1. Create a fresh virtual environment named .venv
python3 -m venv .venv

# 2. Activate the environment:
# On macOS / Linux:
source .venv/bin/activate
# On Windows:
# .venv\Scripts\activate

# 3. Verify the isolated Python path:
which python
# Output: /your/project/path/.venv/bin/python

# 4. Install ML packages into the isolated sandbox:
pip install numpy pandas scikit-learn

# 5. Export exact pinned dependencies:
pip freeze > requirements.txt

# 6. Deactivate when finished:
deactivate
```

---

### 6. Reproducible Dependency Management with `requirements.txt`

A teammate or cloud GPU server can replicate your exact environment with a single command:

```bash
pip install -r requirements.txt
```

#### Version Pinning Best Practices

| Syntax | Example | Meaning |
| :--- | :--- | :--- |
| Exact Pin (`==`) | `torch==2.5.1` | Recommended for production & research reproducibility. |
| Minimum Bound (`>=`) | `numpy>=2.0.0` | Allows automatic updates (can introduce breaking changes). |
| Compatible Release (`~=`) | `scikit-learn~=1.5.0` | Accepts minor patches (`>=1.5.0`, but `<1.6.0`). |

<Callout kind="tip">
  **Always Ignore `.venv/` in Git:** Add `.venv/` and `__pycache__/` to your project's `.gitignore`. Never commit virtual environment binaries to GitHub — commit only `requirements.txt`!
</Callout>
